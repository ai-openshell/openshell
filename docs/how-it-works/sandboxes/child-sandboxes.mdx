A child sandbox is an ordinary sandbox created under a root sandbox. It always runs under its parent's policy and can use only its parent's providers. Agents use child sandboxes to run sub-agents, each in its own sandbox, through a small set of MCP tools.

<Note>
Child sandboxes are experimental. A gateway operator enables them, and the MCP tools, with `experimental_enable_child_sandboxes`. Refer to [Gateway Configuration](/how-it-works/gateways/configuration#child-sandboxes).
</Note>

<Warning>
Delete child sandboxes before you roll back to a gateway version without them or run gateway replicas of different versions. An older gateway drops a child's link to its parent, and the child becomes a root for good.
</Warning>

## Roots and Children

A sandbox created without a parent is a root. A sandbox created with a parent is a child. Only a root can be a parent, so trees are one level deep: a child cannot have children of its own. Apart from the rules on this page, a child behaves like any other sandbox, with the same lifecycle and commands.

## Create and List Children

Create a child with `--parent` and the name of a root in the same workspace. Every other `sandbox create` option works as usual, except `--policy`.

```shell
openshell sandbox create --name lead --from codex-agent:local --provider openai --provider anthropic
openshell sandbox create --name reviewer --parent lead --from claude-agent:local --provider anthropic
```

The gateway refuses a child of a child with `only one level of child sandboxes is supported`. When a root already has as many children as the gateway's `experimental_max_concurrent_children` allows, it refuses with `sandbox 'lead' has reached its limit of 10 children`. Every child counts whatever its state, and keeps its slot until its delete finishes. While one is still being deleted, the refusal says so and you can retry shortly.

`sandbox list` adds a `PARENT` column when the page holds a child. A root shows `-`, and a child whose parent no longer exists shows `deleted (<id>)`. List one root's children with `--parent`:

```shell
openshell sandbox list --parent lead
```

## Policy

A child always uses its parent's policy. When it is created, the gateway copies the parent's latest policy into the child. When the parent's policy changes, the gateway copies the new version into each child at the same time and delivers it to the parent and the children as it delivers any policy update. It does not wait for the parent to load the policy first. A copy that fails is made again within about 30 seconds.

You cannot give a child a policy of its own or change its policy. `sandbox create --parent` refuses `--policy` with `child sandboxes use their parent's policy; omit --policy`, and ignores `OPENSHELL_SANDBOX_POLICY` with a note. Policy updates, approvals and proposals for a child are refused. To change what a child can do, change its parent's policy.

The parent's policy names the parent's filesystem paths, program paths and process user. A child that runs a different image, from `--from` or a template, needs the same user and folder layout as its parent's image. Paths the child's image lacks are skipped, which only removes access, so a child with a different layout can fail to start or find its programs denied. Read the child's startup errors and denials with `openshell logs` or the MCP `logs` tool.

Each sandbox loads its policy on its own and handles a failure through the gateway's policy failure mode. A parent that rejects a policy does not affect its children.

The parent and its children can run different policy versions for a while: until a copy is delivered, or, when the parent rejects a version its children loaded, until the parent loads a later one. If the parent rejects a version that grants more access, its children keep that access, even while the parent is blocked under `fail_closed`.

## Providers

A child can use only providers attached to its parent. Without `--provider`, a child gets all of its parent's providers. With `--provider`, it gets the ones you name, and naming one the parent does not have is refused with `provider 'github' is not attached to parent 'lead'`.

When a provider is detached from the parent, every child stops receiving it at its next configuration update, and the gateway detaches it from the child too. A provider later attached to the parent reaches only children created after that.

## Delete a Parent

The gateway refuses to delete a root that still has children:

```shell
openshell sandbox delete lead
```

```text
sandbox 'lead' has 3 child sandboxes; delete them first
```

Delete the children, then the parent:

```shell
openshell sandbox delete reviewer coder helper
openshell sandbox delete lead
```

A child's results live only inside the child, so this keeps one command from deleting work nobody has collected. If a child's parent record is gone, for example after a failure, the child keeps its last policy and loses all its providers. Delete it.

## MCP Tools

The gateway serves MCP tools at `/mcp` that create and manage sandboxes. Each tool call runs as the matching sandbox RPC, with the same authorization and gateway interceptors as a CLI call. The tools are experimental: their names, arguments and results may change between releases. `tools/list` describes each tool's arguments and results for the caller, a user or a sandbox.

| Tool | What it does |
|---|---|
| `create_sandbox` | Create a sandbox and wait until it is ready, up to 45 seconds. If it is not ready by then, the tool returns its current state with `timed_out: true`, not an error; call it again with the same name to keep waiting. Calling it again returns the existing sandbox with `already_existed: true`. |
| `list` | List sandboxes and their state. |
| `exec` | Run a command and return its exit code and output. |
| `delete` | Delete a sandbox. |
| `logs` | Read a sandbox's own log lines, such as startup errors and policy denials. |

### From Inside a Root Sandbox

An agent in a root sandbox calls `http://openshell.local/mcp`. The sandbox's supervisor attaches the sandbox's credential, so the agent holds no token. A sandbox acts only on its own children:

- `create_sandbox` takes a `name`, and optionally a `template` and `providers`. Without a template, the child copies the root's image, CPU and memory, but not a GPU or other device. With a template, the child gets the template's resources, including a GPU the template requests. A template must carry the label `openshell.ai/agent-usable: "true"` and have no driver configuration. The root's MCP tool list names the templates it may use, with their images, so the agent does not need to be told them. Either way, the child gets the root's runtime class and user namespace setting. Without `providers`, the child gets all of the root's.
- A root created with driver configuration cannot create children through MCP.
- `list`, `exec`, `delete` and `logs` act only on the root's children. Any other name reads as not found.
- The root's network policy does not apply to `openshell.local/mcp`. Any process in the root can call it, even when the policy denies all other traffic or the root is blocked under `fail_closed`.
- A sandbox can have 8 requests to `openshell.local/mcp` open at once. Another one gets `503` with `too many gateway requests at once; try again`.
- The root can create children only while the user who created it is a member of the workspace with at least the user role. A platform admin who is not a member must be added with `openshell workspace member add`. A gateway with no admin role configured treats every authenticated user as an admin and skips this check. A child the root creates records the root as its creator, as `sandbox:<id>`; a child you create with `--parent` records you.

### From the Host

`openshell mcp serve` runs a local MCP server over stdio that forwards each call to the active gateway with your CLI login. It uses the same connection and login as the CLI, including mTLS client certificates, and it refreshes an OIDC login for as long as it runs. Add it to your MCP client's configuration:

```json
{"mcpServers": {"openshell": {"command": "openshell", "args": ["mcp", "serve"]}}}
```

The tools act in the CLI's workspace. To use another workspace, add `"--workspace", "team"` to `args`. Through `openshell mcp serve` you can act on any sandbox the CLI lets you act on. `create_sandbox` takes `name`, `parent`, `image` and `providers`; use the CLI for other create options. The gateway refuses any `/mcp` request that a browser sends, so a web page cannot use your login.

### Run Long Work

The gateway has no background jobs. An agent starts long work detached inside the sandbox and collects it with later `exec` calls. The `exec` tool's description gives the agent a short example. Weaker models may need the full steps below in their instructions.

- `exec` waits up to 30 seconds by default and 45 at most. A command that reaches its timeout is reported as timed out but can keep running in the sandbox. Deleting the sandbox stops it.
- For longer work, such as running a harness, start the command in its own session with its output in files, and write its exit code to a file when it ends.
- To wait, run a short loop with `exec` that checks for the exit code file, at most 25 seconds per call, and repeat it until the file exists.
- Read the output with `tail` or `grep`. Each `exec` reply keeps the first and last 16 KiB of each output stream.
- The files need a writable `/tmp`. A child uses its parent's filesystem policy, so the parent's policy must let `/tmp` be written. The default policy does.
- Nothing stops a second long command in the same sandbox. Use one child for each piece of parallel work.

```text
exec {name: "reviewer", command: ["sh", "-c", "mkdir -p /tmp/jobs/review || exit 1; setsid sh -c 'claude -p \"Review the diff\" > /tmp/jobs/review/out 2> /tmp/jobs/review/err; echo $? > /tmp/jobs/review/exit.tmp; mv /tmp/jobs/review/exit.tmp /tmp/jobs/review/exit' < /dev/null > /dev/null 2>&1 &"]}
→ exit 0
exec {name: "reviewer", command: ["sh", "-c", "for i in $(seq 25); do [ -f /tmp/jobs/review/exit ] && break; sleep 1; done; cat /tmp/jobs/review/exit 2>/dev/null || echo running"]}
→ running, then 0
exec {name: "reviewer", command: ["tail", "/tmp/jobs/review/out"]}
→ the review
delete {name: "reviewer"}
```
